# Master_demo —— ECAT2CAN 主机侧工具包（完全自包含）

Linux 主机侧的 EtherCAT 主站工具，配合跑**港科大 ECAT2CAN 协议**的网关从站使用。

**自包含**：SOEM 已内置在 `third_party/SOEM`，不依赖任何外部路径或环境变量 ——
**拷到任何地方、在任何干净机器上都能一条 `make` 构建完成**。

| 程序 | 用途 |
| --- | --- |
| **`ecat2can_master`** | 诊断 / 实时性测量（扫描、收发、回环延迟、性能基准） |
| **`motor_pos`** | 电机闭环上位机（M3508+C620 / GM6020） |
| `scripts/can-linktest.sh` | 用 SocketCAN 设备（如 PCAN）做 CAN 链路自测 |

运行期只依赖系统 `libc` / `libm`（`ldd` 可验证）。

---

## 1. 支持的从站

| 固件 | 板子 | CAN 通道 |
| --- | --- | --- |
| 港科广 `ECAT2CAN_5e3y`（原版） | 港科广自制板 | 0~3 四路 |
| `Tide_ECAN`（移植版） | **ECAN-Lite** | 0~3 四路 |
| `ecat2can`（单路改编版） | hpm5e3ykit + 外接收发器 | 仅 **3** |

从站把**四路 CAN 总线的收帧**都塞进上行 PDO（每帧带 `can_channel`），
所以主站**不需要预先知道设备插在哪个座子上** —— 用 `scan` 一看便知。

### 协议（192 字节 PDO）

```c
typedef struct {
    uint8_t command;      // 0x00 LOOP_TEST / 0x01 WORK_MODE / 0x02 HW_RESET / 0x03 ONLY_FDB
    uint8_t frame_count;  // 有效 CAN 帧数，最大 17
    uint8_t seq;          // 主站下发序号
    uint8_t status;       // 从站反馈状态
    uint8_t error_flags;  // 从站反馈错误标志
    can_frame_struct can_frames[17];
} ecat2can_tx_rx_message;   // _Static_assert(sizeof == 192)

typedef struct {
    uint8_t  can_channel;   // 0~3 → MCAN0~MCAN3
    uint32_t std_id : 11;
    uint16_t dlc : 4;
    uint8_t  data[8];
} can_frame_struct;         // _Static_assert(sizeof == 11)
```

> `seq` 有**去重语义**：主站 `seq` 不变时从站不会重发。这与从站按
> `(通道, ID)` 去重的收帧逻辑配合，构成完整行为。

## 2. 通道 ↔ 物理座子

| 通道号 | ECAN-Lite 座子 | hpm5e3ykit |
| --- | --- | --- |
| `0` | **CN4** | — |
| `1` | **CN5** | — |
| `2` | **CN9** | — |
| `3` | **CN1** | ✅ 唯一一路 |

> ⚠️ **四个座子是四条电气独立的 CAN 总线** —— 各自独立的 MCAN 控制器和收发器，
> 彼此隔离。设备插在 CN4 就只会出现在通道 0，不会串到别的通道。

## 4. 构建

```bash
make                 # 编译（内部走 cmake + ninja；没有 ninja 自动退回 make）
make setcap          # 加 raw socket 权限（需要 sudo 密码，每次重新链接后都要跑）
```

**不需要先装 SOEM，也不需要 source 任何环境脚本。**

| 命令 | 作用 |
| --- | --- |
| `make` | 编译到 `build/` |
| `make setcap` | 加 raw socket 权限（逐个文件循环调用 setcap） |
| `make run ARGS="..."` | 加权限后跑 `motor_pos` |
| `make linktest ARGS="can0 enp3s0 40"` | 跑 CAN 链路自测 |
| `make install PREFIX=/usr/local` | 安装到系统 |
| `make clean` | 清理 |

**依赖**：编译期 `cmake ≥ 3.28` + C 编译器 + `ninja`（可选）；运行期仅 `libc` / `libm`。

> ⚠️ **每次 `make` 之后必须重跑 `make setcap`** —— 重新链接会生成新文件，
> 内核会把文件 capability 清掉。不加会报
> `打不开网卡 enp3s0（需要 CAP_NET_RAW …）`。
> 自查：`getcap build/ecat2can_master` 有输出才是设上了。

**网卡准备**（EtherCAT 用裸网卡，不能被 NetworkManager 管）：

```bash
sudo nmcli dev set enp3s0 managed no
ip -br link show enp3s0        # 应显示 LOWER_UP
```

## 6. `ecat2can_master` 用法

```
./build/ecat2can_master <网卡名> <命令> [参数...]
```

### 6.1 命令一览

| 命令 | 说明 |
| --- | --- |
| `info` | 进 OP，打印从站信息并周期刷新（Ctrl+C 退出） |
| `loop [次数]` | `LOOP_TEST`：192 字节 PDO 往返一致性校验 |
| **`scan [次数]`** | **多通道扫描：只看不发，统计各通道收帧数与出现过的 ID** |
| `work <通道> <id> [b0..b7]` | 在指定通道以 1 kHz 下发一帧 CAN |
| `workall <id> [b0..b7]` | 在 4 个通道各发一帧（同一拍 PDO） |
| `fdb [次数]` | 只收不发，打印收到的帧（含 `ch=`） |
| `reset` | `HW_RESET`，让从站复位 |
| `bench [次数] [通道]` | EtherCAT 往返分布 + 循环抖动 + CAN 吞吐 |
| `rt [秒数] [通道\|host]` | 实时性合格性测试（直方图 / 截止期错失 / 环境诊断） |
| **`looplat <tx> <rx> [秒数] [Hz]`** | **双 CAN 口回环实时性测试 —— 测「主机 → CAN 总线」的单程延迟** |
| `bench_lat <通道> <can口> [次数]` | 端到端延迟（需 PCAN 挂在同一总线） |

也支持环境变量 `ECAT2CAN_CH=0..3` 设定默认通道。

### 6.2 典型用法

```bash
./build/ecat2can_master enp3s0 scan 3000                      # 找设备在哪一路
./build/ecat2can_master enp3s0 work 0 0x123 11 22 33 44 55 66 77 88
./build/ecat2can_master enp3s0 looplat 2 3                    # 回环实时性（30s @ 1kHz）
./build/ecat2can_master enp3s0 fdb                            # 看总线上的反馈
```

### 6.3 `looplat` —— 双 CAN 口回环实时性测试

**目的**：测出「**主机发出 CAN 指令 → 到达 CAN 总线**」所花的时间，作为控制环
实时性的参考基线，并用于 **Linux 优化前后的对比**。

**接线**：把两个 CAN 座子用两根线短接（**CANH↔CANH、CANL↔CANL**），
例如 ECAN-Lite 的 **CN9（通道 2）↔ CN1（通道 3）**。

```
主机 → EtherCAT → MCAN(tx) → 收发器 → 线 → 收发器 → MCAN(rx) → EtherCAT → 主机
```

> **为什么用这个回路**：全程经过两个**真实收发器和一段真实 CAN 总线**，
> 不含 USB、不含外部设备 —— 正是控制回路实际承受的那一段。
> 用 PCAN 做接收端会把 USB 传输时间算进去，那是虚高的。

**用法**：

```bash
./build/ecat2can_master enp3s0 looplat 2 3               # 默认 30 秒 @ 1 kHz、无负载
./build/ecat2can_master enp3s0 looplat 2 3 15            # 15 秒也够（15000 个样本）
./build/ecat2can_master enp3s0 looplat 2 3 30 1000 5     # 5 帧/拍负载 ≈ 72% 占用
./build/ecat2can_master enp3s0 looplat 2 3 30 1000 8     # 8 帧/拍 ≈ 108%，总线饱和
```

#### 灌总线负载（第 6 个参数）

模拟「**同一条总线上还有其他电机在 1 kHz 上报**」的场景。原理：PDO 每拍最多带
**17 帧**，除回环帧外剩下的槽位都塞成负载帧。

| 帧 | ID | 对应现实 |
| --- | --- | --- |
| 回环帧 | **`0x200`** | C620 控制报文（**最高优先级**）= "控制指令" |
| 负载帧 | **`0x201` ~ `0x210`** | 电机反馈 = "其他电机在 1 kHz 上报" |

> **为什么 ID 要这样选**：CAN 仲裁是**非抢占**的 —— 一帧开始发就必须发完。
> 所以即使回环帧优先级最高，**最多也要等一帧时间（约 130 µs）**。
> 让负载帧用更低优先级的 ID，才是"背景流量"，而不是"抢在指令前面"。

负载与总线占用的对应（标准帧 8 字节，1 Mbps 下单帧约 120 bit）：

| 负载帧 | 总帧/秒 | 估算占用 | 相当于 |
| --- | --- | --- | --- |
| 0 | 1,000 | 12% | 1 台电机 |
| 2 | 3,000 | 36% | 3 台 |
| 4 | 5,000 | 60% | 5 台 |
| 5 | 6,000 | 72% | 6 台 |
| 6 | 7,000 | 84% | 7 台 |
| 8 | 9,000 | 108% | 9 台（**饱和**）|

**上限 16** —— PDO 共 17 个槽位，得留 1 个给回环帧。

> 这也顺带说明一个**真实的系统限制**：同一总线上超过 17 个不同 ID 的设备时，
> 反馈会互相挤占 PDO 槽位。

工具会上报**实际达成率**（不能只看设定值）：

```
  总线占用 : 每拍 6 帧 × 1000 Hz = 6000 帧/秒 → 估算 72%
  负载帧   : 下发 5000 帧/秒 → 实收 4997 帧/秒（达成率 99.9%）
  ✅ 实收≈下发，总线尚未饱和，延迟数据可信。
```

> ⚠️ 一旦饱和，MCAN 发送队列积压，测出来的"延迟"只反映**成功发出的那部分**，
> 实际更糟 —— 所以工具会明确警告。

#### 帧匹配校验（测量有效性）

每次运行都会自证「**每一次往返匹配的都是它自己那一帧**」：

```
── 帧匹配校验 ──────────────────────────────────
  唯一匹配   : 14991 次                                  ✅
  序号断档   : 6 拍  ✅ 与超时数（6）完全一致 → 不是认错帧
  序号异常   : 0 次                                      ✅
  内容回读   : ✅ 8 字节全部原样回来，无位错
  跨拍测量   : 0 次                                      ✅
```

原理见 §7.10。

**运行时的过程显示**（终端上单行原地刷新）：

```
  ⏱  12.3/30s  剩  17.7s │  12345 拍 │ 当前  393 最大  577 均值  393.2 us │ 超时 4
```

> 只在 stdout 是终端时显示（`isatty`）—— **重定向到文件时输出干净，
> 可以直接 `diff` 两次结果做优化前后对比**。

### 6.4 `rt` —— 实时性合格性测试

`bench` 是一次性快照；`rt` 回答的是**"这台机器能不能长期跑住这个周期"**。
额外提供**主机环境诊断**（governor / 调度策略 / CPU 亲和性 / isolcpus / 负载），
并在连从站**之前**打印 —— 连不上时更需要它。

```bash
./build/ecat2can_master enp3s0 rt 10 0        # 带从站
./build/ecat2can_master enp3s0 rt 10 host     # 纯主机模式，不需要任何硬件
```

> 环境诊断里 **`SCHED_IDLE` / `SCHED_BATCH` 会被明确标红** ——
> 这两种策略意味着进程"只在 CPU 没事时才跑"，对实时性是灾难性的，
> 且容易被误显示成"其他"而藏起来。

## 7. 指标解读

`looplat` / `rt` 输出的每个数字对应什么问题，这里逐个说清。

### 7.1 延迟：`p50` / `p90` / `p99` / `p99.9` / `max`

单位都是 **µs**，指一次**往返**（主机发出 → 回到主机）的耗时。

| 指标 | 含义 | 用它回答什么问题 |
| --- | --- | --- |
| `最小` | 最快的一次 | 链路理论上能多快 |
| **`p50`** | 中位数，一半的样本比它快 | **典型延迟**，最常引用的数 |
| `p90` | 90% 的样本比它快 | 稍有波动时的水平 |
| `p99` | 99% 的样本比它快 | **偶发但频繁**的坏情况（每 100 拍 1 次） |
| `p99.9` | 99.9% 的样本比它快 | **罕见但致命**的坏情况（每 1000 拍 1 次） |
| `最大` | 最坏的一次 | 单次极端值，多半是操作系统调度毛刺 |

**为什么不能只看 p50**：p50 是"平时"，控制环的稳定性由**最坏情况**决定。
两个系统 p50 都是 392 µs，但一个 p99.9 是 450 µs、另一个是 900 µs，
**后者需要把增益降到一半**才能稳定。

### 7.2 抖动 `σ`

样本的**标准差**，衡量延迟的**不确定性**。

> **抖动比均值更影响控制性能。**
>
> - **均值**是固定延迟 → 表现为相位滞后，**可以补偿**，也可以在设计时预留
> - **抖动**是不确定延迟 → **无法补偿**，只能按最坏情况留裕度、降低增益
>
> 所以 Linux 调优的目标不是"降低平均延迟"，而是"**削掉尾巴**"。

实测 σ ≈ 26 µs（主机负载中等时）。**抖动主要来自主机调度**，不是链路本身 ——
实测同一套硬件在主机空闲 vs 繁忙时，σ 能差 8 倍。

### 7.3 单程估算与「占控制周期」

```
单程 = 往返 ÷ 2
```

**这是「主机发出 CAN 指令 → 到达 CAN 总线」的那个数。**

| 表达方式 | 例子 | 用途 |
| --- | --- | --- |
| 绝对时间 | `196 us` | 写进文档、和别人对比 |
| **占控制周期** | `0.20 拍`（1 kHz） | **控制环设计时直接用** |

> ⚠️ **单程是粗估**：回路两半不完全对称（CAN 线那 100 多 µs 只占单向），
> 绝对值可能有 **±20% 偏差**。
>
> 但**做优化前后对比时该偏差抵消** —— 对比看的是**变化量**，不受影响。

### 7.4 超时率（丢帧）

一拍内**没收到回环帧**的次数占比。

> **每一次超时 = 控制环丢一次反馈更新。**
>
> 控制环拿到的是上一拍甚至更早的数据，但自己不知道 —— 这会产生
> **状态估计误差**，对 RL 这类依赖观测一致性的算法尤其有害。

判据：

| 超时率 | 评价 |
| --- | --- |
| 0 | 理想 |
| < 0.1% | 良好（每 1000 拍丢不到 1 次） |
| < 1% | 可接受但要注意 |
| ≥ 1% | 该频率下回环跟不上，需降频或优化 |

### 7.5 漂移

**前 1/4 样本的平均** vs **后 1/4 样本的平均**，用来看长时间运行有没有劣化。

| 漂移 | 含义 |
| --- | --- |
| < 5% | ✅ 稳定，可作基线 |
| ≥ 5% | ⚠️ 有热漂移、后台负载变化，或被测对象状态改变 |

> 这个指标必须在**排序之前**算 —— 排序后数组就丢了时间顺序，
> 拿到的会变成"最小 1/4 → 最大 1/4"，那是分位数差不是漂移。
> （本工具踩过这个坑，曾稳定误报 +16% 的假漂移。）

### 7.6 直方图

**只看分位数看不出分布形状。** 直方图能区分：

| 形状 | 含义 |
| --- | --- |
| 单峰窄 | 理想，延迟集中且可预测 |
| 单峰宽 | 抖动大 |
| **双峰** | 有两条不同的路径 / 两种状态（例如偶尔跨拍） |
| **长尾** | 偶发严重拖延（调度毛刺），此时 p99 会低估 |

### 7.7 调优要看尾部，不要看均值

> **均值由链路物理决定，Linux 调优改变不了。**
> CPU 隔离、RT 优先级、关后台负载 —— 这些改善的都是**尾部的毛刺**。

所以对比优化前后：

| 该看 | 不该只看 |
| --- | --- |
| `p99` / `p99.9` / `max` / `σ` | `平均`（几乎不变） |

### 7.8 实测基线（30 s @ 1 kHz，两次独立复测）

| 指标 | 第 1 次 | 第 2 次 |
| --- | --- | --- |
| 样本 | 29965 / 30000 | 29975 / 30000 |
| 最小 | 319 µs | 318 µs |
| **p50** | **393 µs** | **392 µs** |
| p90 | 422 µs | 422 µs |
| p99 | 444 µs | 446 µs |
| 平均 | 393.2 µs | 391.9 µs |
| **抖动 σ** | **26.2 µs** | **26.3 µs** |
| 超时率 | 0.117% | 0.083% |
| 漂移 | +0.29% | +0.26% |

**单程估算**：

```
p50 = 196 us  =  0.20 个控制周期（1 kHz）
p99 = 222 us
往返 393 us < 1000 us  ✅ 单拍内完成，不跨拍（余量 607 us）
```

主指标复测高度一致（p50 差 0.25%、p90 完全相同、σ 差 0.1 µs）→ **可作为基线**。
尾部两次有差异属正常，那正是调优要改善的部分。

**这个基线怎么用**：

```bash
# 优化前
./build/ecat2can_master enp3s0 looplat 2 3 > before.txt

# —— 做 Linux 调优（见下）——

# 优化后
./build/ecat2can_master enp3s0 looplat 2 3 > after.txt

# 对比（过程显示不会写进文件，两者格式一致可直接比）
diff before.txt after.txt
```

**Linux 调优顺序**（按收益排序）：

1. **CPU 调频** → `sudo cpupower frequency-set -g performance`
2. **调度策略** → `sudo chrt -f 80 ./build/ecat2can_master ...`
   （用 `rt` 确认它不是 `SCHED_IDLE` / `SCHED_BATCH`）
3. **CPU 隔离** → 内核参数 `isolcpus=2,3 nohz_full=2,3 rcu_nocbs=2,3`，
   再 `taskset -c 2` 绑到隔离核
4. **关掉后台负载**

### 7.9 总线负载的影响（实测梯度）

用 §6.3 的负载注入，同一条总线上跑三档（每次 15~30 秒，独立运行）：

| 负载 | 估算占用 | p50 往返 | 单程 p50 | 抖动 σ | 超时率 |
| --- | --- | --- | --- | --- | --- |
| **0** | 12% | **393 µs** | 196 µs | 24.2 µs | 0.077% |
| **4 帧** | 60% | 410 µs | 205 µs | 23.7 µs | 0.143% |
| **5 帧** | 72% | 411~414 µs | 205~207 µs | 22.0~24.0 µs | 0.040% |

**两个稳定结论：**

**① 延迟从空载到有负载跳一次（+18 µs，+4.6%），然后就进入平台。**
60% 和 72% 的 p50 几乎一样。这符合 CAN 非抢占仲裁的物理机制 ——
等待时间取决于"撞上正在发帧"的概率，而 60%→72% 在均值层面差别不明显。

**② 抖动 σ 始终在 22~24 µs 不变。** ⭐

> **负载增加的是「固定的仲裁等待」（可补偿），而不是「随机的不确定性」（不可补偿）。**
>
> 对控制环的意义：**延迟变长约 5%，但增益不需要因此下调。**

> ⚠️ `max` / `p99.9` 在三次跑之间波动较大（873 ~ 1720 µs），**这是运行间波动，
> 不是负载的功劳或过错**。跨运行比较只看 p50 / σ。

### 7.10 「这次测量可信吗」—— 帧匹配校验

**问题**：怎么确定每一次往返测量的都是**这一拍发出去的那一帧**，
而不是上一拍的残留帧？

**匹配机制**（三个条件同时成立）：

```c
/* 发的时候把 16 位序号写进数据前两字节 */
data[0] = (uint8_t)(i >> 8);
data[1] = (uint8_t)(i & 0xFF);

/* 收的时候必须同时满足 */
f->can_channel == rx_ch        // ① 必须是接收通道
&& f->std_id   == 0x200        // ② 必须是指定 ID
&& f->data[0]  == 高字节        // ③ 16 位序号完全对上
&& f->data[1]  == 低字节
```

**为什么不会搞混：**

| 疑问 | 保证 |
| --- | --- |
| 上一拍的残留帧？ | 序号不匹配，直接跳过 |
| 重复计数？ | 每拍只取第一次匹配就 `break` |
| CAN 帧会不会乱序？ | **不会** —— 同一条总线上先发的帧一定先到（物理保证） |
| 16 位序号回绕？ | 1 kHz 下 65.5 秒回绕一次；要误判需有帧延迟**正好 65.5 秒**才到 |
| 是不是片内自环？ | **收到的通道 ≠ 发送的通道**；且**不接线就一帧都收不到**（实测验证过） |

**运行时的自证输出：**

```
  唯一匹配   : 14991 次
  序号断档   : 6 拍  ✅ 与超时数（6）完全一致 → 断档全部来自超时，不是认错帧
  序号异常   : 0 次  ✅ 没有把更早的帧当成这一拍
  内容回读   : ✅ 8 字节全部原样回来，无位错
  跨拍测量   : 0 次  ✅ 回声都在一个控制周期内回来
```

**`序号异常 = 0` 且 `断档数 = 超时数` —— 两条同时成立，才说明每次往返都在测各自那一帧。**

> **交叉验证是关键**：断档数如果和超时数对不上，就说明有不属于超时的断档，
> 匹配逻辑有问题 —— 这个检验会**自己暴露**故障。

**已知的精度边界**（不是 bug，是方法的天花板）：

> 轮询一次要花 **~66 µs**（一次 EtherCAT 往返），所以检测到的到达时刻有
> **+0~66 µs 的固定偏大**。这是当前方法的精度上限。

### 7.11 一次 EtherCAT 往返 66 µs 花在哪

很多人会问 66 µs 是否合理。算一下就清楚了：

| 帧组成 | 字节 |
| --- | --- |
| 前导码 + SFD | 8 |
| 目的 / 源 MAC | 12 |
| EtherType + EtherCAT 帧头 | 4 |
| 数据报1：头 10 + **输出 PDO 192** + WKC 2 | 204 |
| 数据报2：头 10 + **输入 PDO 192** + WKC 2 | 204 |
| FCS | 4 |
| **帧总长** | **436 B** |
| + 帧间隔 IPG | 12 |
| **线上占用** | **448 B** |

```
448 B × 8 bit ÷ 100 Mbps = 35.8 µs
```

EtherCAT 的 ESC 是**直通（cut-through）**转发 —— 边收边转发，不等整帧收完。
所以往返 ≈ 一次串行化 + 少量 ESC 延迟 ≈ **36 µs**。

**与实测对比：**

| | 值 | 是什么 |
| --- | --- | --- |
| **物理下限** | **≈ 36 µs** | 改不了（帧大小 + 100 Mbps 都是定的）|
| 实测 `bench` **min** | **53 µs** | 比下限高 **17 µs** = **主机软件开销**（socket 收发 + memcpy + 调度）|
| 实测 `bench` **p50** | **66 µs** | 比 min 再高 **13 µs** = **调度抖动** |

> **✅ 66 µs 是合理的，链路层没有异常。**
>
> **能优化的只有主机侧那 17 + 13 µs** —— 物理的 36 µs 谁也动不了。
> 这也说明：**优化均值意义有限，真正该优化的是尾部抖动。**

### 8.4 两种电机的差异

| | M3508 + C620 | GM6020 |
| --- | --- | --- |
| 控制报文 | `0x200`(ID1~4) / `0x1FF`(ID5~8) | **`0x1FE`**(ID1~4) / **`0x2FE`**(ID5~7) |
| 反馈报文 | `0x200+ID`（0x201~0x208） | **`0x204+ID`**（0x205~0x20B） |
| 控制量 | 转矩电流，满量程 20A | 转矩电流，满量程 **3A** |
| 减速比 | 19.2（或 1，不带减速箱） | **1**（直驱） |
| 编码器 | 相对 | 绝对 |
| 反馈 `[7]` | 电机错误码 | Null（恒 0） |
| 最大空载转速 | 转子 9400 rpm / 轴 ~490 rpm | **320 rpm** |
| 额定扭矩 | 0.16 N·m（转子） | **1.2 N·m**（轴上） |
| 空载电流 | 0.6 A | 78 mA |

> ⚠️ `0x1FF` 对 C620 是"电调 5~8"，对 GM6020 是"驱动器 1~4" —— 语义不同但报文字节相同。
> 程序按 `--motor` 自动选对，**但同一条总线上别混用会冲突的 ID**。

**GM6020 电流模式的前提**：固件 ≥1.0.11.2，且用 **RoboMaster Assistant（≥2.7）
打开"电流环开关"**。否则电机对 `0x1FE` / `0x2FE` 毫无反应。

> **排查方法**：使能后电机完全不动 → 加 `--gm-voltage` 试电压模式。
> 能动就说明是电流环开关没开。

**GM6020 的 ID**：由拨码开关 Bit[2:0] 设置（`000` 无效），第 4 位控制 CAN 终端电阻接入。

#### 环路架构：为什么主机不做电流环

三级串级是「**主机：位置环 + 速度环 → 电流指令；驱动器：电流环**」：

```
位置环(角度→rpm) → 速度环(rpm→电流) → [驱动器内部电流环] → 电机
└────────── 主机侧，1 kHz ──────────┘└── 驱动器内部，几 kHz ──┘
```

**主机侧再套一层电流环是有害的**：

| | 驱动器内部电流环 | 主机侧电流环 |
| --- | --- | --- |
| 反馈延迟 | 微秒级（芯片内部） | **~1.4 ms**（EtherCAT + CAN + 驱动器周期） |
| 可达带宽 | 几 kHz | 理论上限 ≈ `1/(4×1.4ms)` ≈ **180 Hz** |

**用 180 Hz 的慢环去套几 kHz 的快环，只会增加相位滞后、把系统搞得更不稳。**
所以电流环必须留在驱动器里。`--cur-loop` 保留这个开关，是为了让你能亲自验证。

#### 反馈里有四个量，分别闭哪个环

| 字节 | 内容 | 闭哪个环 |
| --- | --- | --- |
| **`[0..1]`** | **机械角度** `0~8191`（一圈 8192 计数） | **← 位置环就是靠它** |
| `[2..3]` | 转速 rpm | ← 速度环 |
| `[4..5]` | 实际转矩电流 | ← 驱动器内部电流环（主机用它监视/限幅） |
| `[6]` | 温度 | 保护 |
| `[7]` | 错误码 | 保护 |

**"转矩电流"和"电流指令"是同一个物理量** —— FOC 电机满足 `τ = Kt × I`，
站在电机输出看是"转矩"，站在驱动器输入看是"电流"。所以指令和反馈**可以直接相减**。

位置环靠 `[0..1]` 的机械角度按 13 位增量累积成多圈角度得到。

### 8.5 状态栏怎么读

终端**最后两行**是状态栏，上方是命令与消息（两者不会互相覆盖）：

```
[使能] 位置   -12.34° →    90.00°    电流    0.42/   1.00A
       转速    -520 [  -480] rpm      30℃  E0    68us
        │        │        │      │        │      │     │    └ EtherCAT 往返耗时
        │        │        │      │        │      │     └ 错误码（C620 才有意义）
        │        │        │      │        │      └ 电机温度
        │        │        │      │        └ 指令电流
        │        │        │      └ 实测电流
        │        │        └ 目标位置（输出轴角度）
        │        └ 当前位置（输出轴角度）
        └ 失能 / 使能 / 开环
                                                转速行 [ ] 里是速度环给出的目标转速
```

> 为什么要两行：单行接近 **100 列**，80 列终端会被截断，把温度、错误码和
> `(等反馈)` 这些关键信息切掉。拆成两行后每行 55 / 49 列，任何终端都放得下。

**`电流 实测/指令` 是最有用的诊断字段：**

| 观察 | 结论 |
| --- | --- |
| 两个数贴得很紧 | 驱动器电流环工作正常 |
| 指令有值、实测长期≈0 | 电流环没工作（GM6020"电流环开关"没开），或电机三相线没接 |
| 实测长期顶在 ±3A 但电机不动 | 机械卡死，或堵转过热保护 |
| 两个数符号相反 | 反馈量纲/符号约定不对，先别使能，核对 `--id` 和 `--motor` |

末尾出现 `(等反馈)` 表示**还没收到电机反馈**，此时所有联锁都会阻止使能。

**输出重定向到文件时**自动退化成逐行打印，方便采集：

```bash
./build/motor_pos enp3s0 --motor m3508 --ch 0 --limit 3 --log-ms 100 --monitor > run.log
```

### 8.6 首次上车流程

> ⚠️ **每一步都确认电机已固定牢**。M3508 带减速箱时输出扭矩能把碳纤维件掰断；
> GM6020 直驱满速 320 rpm，甩起来一样危险。

**第 1 步：只读监视，确认链路**

```bash
./build/motor_pos enp3s0 --motor <类型> --ch <通道> --id <ID> --monitor
```

手动慢慢转电机轴，观察：**位置**跟着变 → 反馈链路通；**转速**有正负变化；
**温度**合理；**错误码**为 0（C620；`3` 表示三相线没接好）。

**第 2 步：小电流开环，确认方向和力度**

```bash
./build/motor_pos enp3s0 --motor m3508 --ch 0 --id 1 --limit 1
```

按 `e` 使能，然后 `c 1` 给 1A 正向、`c -1` 反向、`c 0` 退出。

**方向约定**：`c` 给正值时位置读数应该**增大**。记下来，第 3 步会用到。

**第 3 步：小角度位置闭环**

```
e          使能（目标=当前位置，轴应该被"锁住"，手拧有抗力）
2          目标转到 2°
```

**如果误差越来越大、往一个方向冲**，说明闭环符号反了 → `d` 立刻失能，
然后加 `--invert-spd` 重启。（发散保护也会在 0.5 s 后自动切断输出并提示。）

**第 4 步：逐步放大**

```bash
./build/motor_pos enp3s0 --motor m3508 --ch 0 --id 1 --limit 10 --max-rpm 2000
```

### 8.7 PID 整定

串级结构：`位置环（输出轴角度 → 目标转子 rpm）→ 速度环（rpm → 电流）→ 驱动器内部电流环`

#### ⚠️ 先理解这条链路的延迟

主机 → EtherCAT → CAN → 电机 → CAN → EtherCAT → 主机，**实测约 1.4 ms**
（= 本工具实测的网关单程 196 µs × 2 + 驱动器自身两个 1 kHz 周期约 1 ms）。

> 早先的文档按 **3~4 ms** 估算，据此得出"带宽超 80 Hz 就自激"。
> 实测后修正为 **~1.4 ms**，理论带宽上限约 **180 Hz**。
> 但整定仍从保守默认值开始 —— 实际可达带宽还受机械谐振、摩擦、减速箱回差限制。

两个后果：

1. **增益不能按"本地闭环"来给。** 先在这个基础上**慢慢往上加**，不要一上来就翻倍。
2. **微分项必须滤波。** 位置是累积的 13 位机械角度（量化 0.044°），而且电机反馈
   1 kHz 与 EtherCAT 1 kHz **不同步**，网关偶尔会读到重复帧，使 `(本次-上次)`
   在 0 和 2 倍之间跳。不滤波的微分会变成几百 Hz 方波直接嗡起来。

   所以：**`--filter-ms` 默认 5 ms（不要设成 0），`kd` 默认 0。**
   阻尼交给速度环提供就够了。

**默认增益**（两种电机差别很大，程序按机型自动选）：

| | 位置环 kp | 位置环 kd | 速度环 kp | 速度环 ki |
| --- | --- | --- | --- | --- |
| M3508 + C620 | 8 | 0 | 20 | 0.2 |
| **GM6020** | **4** | **0** | **4** | **0.05** |

GM6020 是直驱、转矩常数大（1.2 N·m / 3A）、惯量小，同样的增益在它身上会自激。

#### 速度环

```
c 0          先退出开环
kp 0         位置环比例关掉
e            使能
```

用手拧轴然后松手，看回弹：

| 现象 | 调整 |
| --- | --- |
| 回弹发软、慢 | `skp` 加大（**每次 ×1.5，不要翻倍**） |
| 抖动、嗡嗡响 | `skp` 减半 |
| 稳态有小偏差 | `ski` 稍加 |

#### 位置环

```
kp 4         从默认值开始往上加（先试 2 → 4 → 8）
2            给个小目标看响应
```

| 现象 | 调整 |
| --- | --- |
| 到位慢 | `kp` 加大 |
| 超调、来回摆 | 降 `kp`；仍不够再加一点 `kd`（0.05 → 0.2） |
| **高频抖** | 先降 `skp`，再降 `kp`；确认 `--filter-ms` 没设成 0 |

#### 自激了怎么办

程序会自己检测：**输出量在 0.2 s 内换向超过 30 次**就判定自激并打印警告。

```
d            立刻失能
skp 2        速度环先降到默认的一半
kp 2         位置环也降
e            重新使能
```

仍不稳就加大 `--filter-ms`（5 → 10 → 20 ms）—— 滤波会引入相位滞后，
但对抗这条链路的延迟和重复帧跳变很有效。

> 主机侧 1 kHz 的抖动还取决于内核。正经控制建议上 **PREEMPT_RT**，
> 或者 `chrt -f 50 ./build/motor_pos ...` 提优先级。
> 用 `rt` 和 `looplat` 可以量化这两者的差别。

### 8.8 安全机制

内置联锁（都会**自动切断输出**并打印原因）：

| 机制 | 阈值 |
| --- | --- |
| 反馈超时 | 100 ms 收不到反馈 |
| 温度过高 | ≥ 100 ℃ |
| 驱动器错误码 | 非 0（C620） |
| 闭环发散 | 位置误差连续 0.5 s 增大 |
| 输出限幅 | `--limit` |
| 转速限幅 | `--max-rpm` |
| 目标角度限幅 | ±7200° |

其他：**上电默认失能**，必须手动按 `e`；**使能瞬间目标 = 当前位置**，不会窜出去；
退出（`q` 或 Ctrl+C）时**先发 100 个周期零输出**再关网卡；
`--monitor` 模式下按 `e` 无效，输出恒为 0。

## 9. CAN 链路自测（`can-linktest.sh`）

用一个已知正常的 SocketCAN 设备（如 PCAN-USB）验证网关某一路的收发：

```bash
sudo ip link set can0 type can bitrate 1000000 sample-point 0.75
sudo ip link set can0 up
./scripts/can-linktest.sh can0 enp3s0 40
```

它会自检 `can0` 的网卡层 / CAN 层状态、统计 `cansend` 成败、并打印网关收到的帧。
**改线之后先跑这个。**

> ⚠️ 两个坑：
> - PCAN-USB **每次重新插拔都会掉回 DOWN**，必须先重配 bitrate 再 up
> - **`cansend` 返回 0 只代表帧进了发送队列，不代表总线上有人 ACK。**
>   判断链路通不通，唯一有效的判据是**网关是否真的收到了帧**

## 10. 排错速查

| 现象 | 原因 / 处理 |
| --- | --- |
| `打不开网卡` | 没 setcap（重新 `make` 后要重设） |
| `没扫到 EtherCAT 从站` | 网关没上电 / 网线没插 Port0 / 网卡没有 `LOWER_UP` |
| `期望 PDO 192/192，实际 x/y` | 从站固件和上位机的协议版本不匹配 |
| 一直 `(等反馈)` | ① **CAN_H/CAN_L 接反** ② 电机没供电 ③ `--id` / `--ch` 不对 ④ 网关通道和接线不一致 |
| 反馈的**错误码=3** | 电机三相线与电调没接好 |
| 使能后电机完全不动 | GM6020 可能是电流环开关没开 → 加 `--gm-voltage` 验证 |
| 使能后往一个方向冲 | 闭环符号反了，加 `--invert-spd` |
| **高频抖动 / 嗡嗡响** | 增益相对链路延迟过大。先 `d` 失能，然后 `skp` 减半、`kp` 减半；仍抖就加大 `--filter-ms` |
| 电流实测和指令长期对不上 | 驱动器电流环没工作，或电压模式下量纲不同 |
| 某一路 CAN 怎么接都不通 | 见 Tide_ECAN 移植记录：检查该路 `init_*_pins()` 有没有被重复配置 |
| 半小时后突然全断 | 网关 MCAN 进了 bus-off。固件已有自动恢复；旧版本需复位板子 |

**排错顺序**：先用 `ecat2can_master` 确认链路，再看电机。

```bash
./build/ecat2can_master enp3s0 info      # 1) 从站和 PDO 正常吗
./build/ecat2can_master enp3s0 loop      # 2) 192 字节 PDO 往返
./build/ecat2can_master enp3s0 fdb       # 3) 网关收到的每一帧（含 ID/DLC/数据）
./build/ecat2can_master enp3s0 scan      # 4) 设备挂在哪一路
```

`fdb` 特别有用：如果电机在发反馈，这里能看到；**如果这里什么都没有，
问题就在网关之前或 CAN 物理层**。

### 寄存器判读（定位 CAN 物理层问题）

| MCAN 状态 | 含义 |
| --- | --- |
| `ECR.REC` 持续上升 + `PSR.LEC` 报错 | **信号来了但解不开** → CANH/CANL 接反、波特率不对 |
| `ECR = 0` + `PSR.ACT = Synchronizing` | **总线被持续摁成显性** → 收发器故障 / 引脚复用冲突 |
| `ECR = 0` + `PSR.ACT = Idle` | **无信号** → 线没通、对端没发、收发器没工作 |
| `PSR.ACT = 2 (Receiver)` + `LEC = 0` | **正在正常收帧** ✅ |

> `PSR`：`ACT` = bits[4:3]（掩码 `0x18`），`LEC` = bits[2:0]（掩码 `0x07`）；
> `ECR`：`TEC` = bits[7:0]，`REC` = bits[14:8]。

### 如果不想内联 SOEM

把 `third_party/SOEM` 从仓库移除，改用 CMake 的 `FetchContent` 在配置阶段自动拉取：

```cmake
include(FetchContent)
FetchContent_Declare(SOEM
  GIT_REPOSITORY https://github.com/OpenEtherCATsociety/SOEM.git
  GIT_TAG        v2.0.0)
set(BUILD_SHARED_LIBS OFF CACHE BOOL "" FORCE)
set(SOEM_BUILD_SAMPLES OFF CACHE BOOL "" FORCE)
FetchContent_MakeAvailable(SOEM)
```

这样仓库里不含 SOEM 源码，但**首次构建需要联网**。
