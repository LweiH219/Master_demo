# Master_demo 主机实时性测试与优化

> 文档类型：历史测试报告  | 测试日期：见正文  | 状态：历史记录


测试日期：2026-10-15，时间按北京时间。主机：`tide@10.191.242.222`；项目：`/home/tide/Master_demo`。

## 结论

这台主机在本次 1 kHz 纯主机试验中表现良好。FIFO 80 明显改善空闲时的周期抖动；全核 performance 可降低常见唤醒延迟，但与睿频一起使用时温升较大，最坏延迟也没有一致改善。推荐优先使用 FIFO，并考虑测试通过的临时低温配置，而不是直接永久开启全核 performance。

所有调频和睿频试验均已恢复原设置。未修改启动参数、CPU 隔离、IRQ 亲和性或系统服务，未重启。新增可复测脚本和项目内报告。

## 环境与测量方法

- Ubuntu 24.04.5 LTS；`6.8.1-1060-realtime` PREEMPT_RT。
- i7-13620H，16 个逻辑 CPU；0–11 是六个带 SMT 的核心，12–15 是四个单线程核心。
- 初始 `intel_pstate=active`，全部 governor 为 `powersave`，EPP 为 `balance_performance`，睿频开启；无 CPU 隔离；时钟源 TSC。
- 项目自带 `ecat2can_master enp3s0 rt 30 host`：1000 Hz，每组 29999 个相邻周期样本。
- 独立工具 `cyclictest` 2.50：FIFO 80、锁内存、每 CPU 一个线程、周期 1000 µs、每组 30 秒，合计约 48 万个唤醒样本。默认加 `--default-system`，不额外设置 PM QoS。
- 表中的 cyclictest 分位数由所有 CPU 的直方图合并计算，最大值取所有线程最大值，直方图无溢出。
- 测试按顺序执行，后台日常服务保留。有限样本与顺序测试存在环境波动，不能将每个差值都解释成确定的因果收益。

## 项目周期测试

这里测的是相邻周期长度，目标为 1000 µs，**不是唤醒延迟**。

| 空闲配置 | p99 | p99.9 | 最大周期 | 抖动 σ | 周期 >1100 µs |
| --- | ---: | ---: | ---: | ---: | ---: |
| powersave + 普通调度 | 1006 µs | 1034 µs | 1072 µs | 3.2 µs | 0 |
| powersave + FIFO 80 | 1003 µs | 1008 µs | 1025 µs | 1.4 µs | 0 |
| performance + FIFO 80 | 1000 µs | 1003 µs | 1048 µs | 0.9 µs | 0 |

FIFO 相比普通调度使 σ 降低约 56%。再开启 performance 时 p99.9 继续改善，但最大周期反而增加；因此不能声称已经改善所有最坏情况。

## 绝对唤醒延迟

| 配置 | p50 | p99 | p99.9 | 最大值 |
| --- | ---: | ---: | ---: | ---: |
| 空闲 powersave + FIFO 80 | 6 µs | 12 µs | 15 µs | 36 µs |
| 空闲 performance + FIFO 80 | 1 µs | 3 µs | 5 µs | 54 µs |
| 空闲 performance + FIFO 80 + PM QoS=0 | 1 µs | 3 µs | 5 µs | 31 µs |

performance 的 p99.9 在这组观测中降低约 67%，但 max 增大。额外 PM QoS 组仅 max 变化，分位数相同，且 cpuidle driver 为 `none`；没有足够证据证明 PM QoS 有独立收益，因此未默认加入脚本。

## 温度限制与低温配置

8 个持续计算进程测试中，两种 governor 都触及 90°C 停止线。撤除负载后的周期和 cyclictest 结果保留，但**不作为有效的持续负载对照**。

改为 4 个约 50% 占空比的 nice 10 计算进程后，powersave 全程完成、最高 74°C：项目 p99.9 1004 µs、最大周期 1013 µs、σ 0.8 µs；cyclictest p99.9 8 µs、max 20 µs。performance 仍超过 85°C 停止线，采样温度最高 89°C，因此该组也不作为完整负载测试结果。

追加测试 performance + FIFO 80 + 关闭睿频（原 no_turbo=0，试验期间=1）：

| 测试 | 周期 p99.9 | 最大周期 | σ | >1100 µs |
| --- | ---: | ---: | ---: | ---: |
| 空闲，15 秒 | 1003 µs | 1012 µs | 0.7 µs | 0 |
| 4 个间歇进程，30 秒 | 1006 µs | 1016 µs | 1.1 µs | 0 |

低温配置的同条件负载持续完成，最高观测温度 **57°C**；独立 cyclictest 累计 **479978** 样本，p99 **6 µs**、p99.9 **8 µs**、最大 **16 µs**，无 >100 µs 唤醒样本。相比有效的 powersave 负载组，p99.9 相同，max 从 20 变为 16 µs、温度从 74 降到 57°C，但项目周期 p99.9 和 σ 略差。这说明它可作为兼顾温度与延迟的候选配置，不能声称全面胜出。空闲组时长不同，也不作严格等样本比较。关闭睿频会降低较重控制计算任务的吞吐，需要再测真实业务的执行时间。

温度为每两秒读取 thermal zone 的观测值，停止线是本次试验约束，不代表厂商温度上限。低负载进程用固定工作量和等长休眠模拟约 50% 占空比，未硬绑定 CPU；这不是满载、内存、磁盘与网络的综合压力测试。较早一组高负载脚本在撤除负载时有子进程信号处理回溯，已修正，后续组正常退出。

## 如何复测

在远端项目目录运行：

```bash
cd /home/tide/Master_demo
sudo ./scripts/rt-host-test.sh 30 current
sudo ./scripts/rt-host-test.sh 30 performance-no-turbo
```

第一条保留当前电源配置；第二条临时启用 performance 并关闭 Intel 睿频。两者均以 FIFO 80 运行项目纯主机测试，然后运行锁内存的 cyclictest，每项各持续指定秒数。脚本输出周期结果、唤醒分位数和日志位置。

脚本还支持 `performance`，供对照试验。使用互斥锁避免脚本自身并发，退出或收到 INT/TERM 后恢复 governor、EPP 和该模式调整过的睿频设置。脚本依赖 `cyclictest`、`chrt`、`python3`、`flock`。运行期间不要由其他工具同时修改电源策略；SIGKILL/断电不能触发清理。

## 结论边界

项目现有输出中“截止期错失”实际为相邻周期 **>1100 µs**，且短周期与长周期可能补偿；它不等同于严格 1000 µs 绝对截止期，也未计入真实控制任务的最坏执行时间。现有输出“可直接用于硬实时控制”的措辞偏强，本报告不采用这一判定。整数微秒统计会产生量化误差，例如报告均值约 999.5 µs，不能据此推断调度频率漂移。

本次使用 host 模式，没有进行 CAN 回环、EtherCAT 往返或电机驱动。主机测试不能代替端到端链路验证；下一步应在确认回环接线与总线设备状态后，按 README 使用 `looplat` 进行同条件对比。CPU 隔离、IRQ 设计和长时间带真实业务的测试需结合最终部署再进行。
